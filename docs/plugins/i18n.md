# Plugin i18n

How plugins ship translations. Each plugin owns one or more **namespaces**, declares them in `plugin.json`'s `i18nNamespaces`, and the host loads and switches locales for you — this page shows the layout that makes that work, for the org-plugin case first (the main consumer of this mechanism) and the single-bundle case after.

## The mechanism

- A **namespace** groups one UI's strings: kebab-case, `<plugin-id>` or `<plugin-id>-<module>`.
- `plugin.json` declares every namespace the plugin ships in `i18nNamespaces` (multi-module manifests can also declare them per `modules[]` entry).
- Locale files are plain JSON, one file per language, per namespace: `locales/<namespace>/<lng>.json`.
- Components resolve keys as `t("<namespace>:<key>")` via `usePluginTranslation` from `@oc-mui/i18n`.
- The host serves the files and tells i18next where they live — in dev via the `.local-plugins` manifest, in production via the JAR's `plugins.json` entry (`localesUrl` + namespace list). You never wire i18next yourself.

## Worked example: an org plugin

An org plugin (its own repo, mounted at `.local-plugins/<org>/`, shipped as a JAR) is typically multi-module, and each module carries its own namespace and locale folder:

```
.local-plugins/acme/
├── plugin.json                # "i18nNamespaces": ["acme-header", "acme-footer"]
└── modules/
    ├── header/
    │   ├── locales/
    │   │   └── acme-header/
    │   │       ├── en.json    # { "logout": "Log out" }
    │   │       └── de.json    # { "logout": "Abmelden" }
    │   └── … module code
    └── footer/
        └── locales/
            └── acme-footer/
                ├── en.json
                └── de.json
```

```tsx
import { usePluginTranslation } from "@oc-mui/i18n";

export function AcmeHeader() {
  const { t } = usePluginTranslation(["acme-header"]);
  return <button>{t("acme-header:logout")}</button>;
}
```

`usePluginTranslation` auto-loads the namespace on first render and follows the host's locale switching. (Plain `useTranslation` from `react-i18next` works too, but then loading the namespace is your problem.)

That's the whole authoring story. Serving is automatic in both environments:

- **Dev** (`pnpm dev` with the plugin under `.local-plugins/`): the dev server discovers every `modules/*/locales/<ns>/` folder, serves the files, and announces the namespaces in `/local-plugins/manifest.json` — the shell registers them with i18next on load.
- **Production (JAR)**: the locale folders ship inside the JAR; the backend lists each plugin's namespaces and locale URL in `plugins.json` (see the `Management-Plugin-I18n` header in [distribution.md](./distribution.md#build)), and the shell registers them the same way.

## Single-bundle plugins (the scaffold layout)

A scaffolded single-bundle plugin keeps its locales at the plugin root — no `modules/`:

```
.local-plugins/hello/
├── plugin.json                # "i18nNamespaces": ["hello"]
└── locales/
    └── hello/
        ├── en.json
        └── de.json
```

This is the canonical manifest layout: the contract test's parity check reads it, and the scaffolded JAR build ships it. A different location can be declared via `plugin.json`'s `locales` field (a relative path with the same `<locales>/<namespace>/<lng>.json` structure inside).

> **Dev-mount limitation.** The `.local-plugins` dev server currently discovers locale files **only** in the `modules/<module>/locales/` layout above. A root-level `locales/` passes the contract test and ships correctly in the JAR, but the dev shell renders its keys untranslated. To see the strings live in dev, mirror the namespace folder to `modules/<any-name>/locales/<namespace>/` and restart `pnpm dev`.

## Two rules the tooling enforces

**Key parity.** The contract test's `expectI18nKeyParity()` fails when locale files of the same namespace have mismatched key sets — if `en.json` has `"logout"`, `de.json` must too. Keys may be nested; parity compares dotted paths (`buttons.save`). To check only specific locales, pass them: `expectI18nKeyParity(["en", "de"])` — see [`@oc-mui/plugin-testing`](../../packages/plugin-testing/README.md).

**No hot reload for locale JSON.** i18next loads each namespace once at init. A key added while `pnpm dev` runs renders as the raw key until you **restart the dev server**. Production builds always bundle the current keys — this is a dev-loop quirk, not a missing-translation bug.

## Conventions

- Namespace names: kebab-case, `<plugin-id>` or `<plugin-id>-<module>` (`acme-header`, `acme-footer`).
- Key names: scoped semantically (`buttons.save`, `errors.network`), not by component path — restructuring components shouldn't break translations.
- Don't reference another plugin's namespace; add the key to your own.
