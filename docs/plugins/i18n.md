# Plugin i18n

Translations are namespaced by plugin. Each plugin owns its namespace; the host loads everything through `@oc-mui/i18n`.

## Layout

```
my-plugin/
├── plugin.json           # i18nNamespaces: ["my-plugin"]
└── locales/
    └── my-plugin/        # one folder per namespace
        ├── en.json
        └── de.json
```

A single plugin can ship more than one namespace — typically when it has multiple distinct UIs (e.g. a header + a sidebar). List every namespace in `plugin.json`.

## Reference a key

```tsx
import { usePluginTranslation } from "@oc-mui/i18n";

export function MyView() {
  const { t } = usePluginTranslation(["my-plugin"]);
  return <h1>{t("my-plugin:welcome")}</h1>;
}
```

`usePluginTranslation` is the hook plugins should use — it auto-loads the namespace on first render and respects the host's locale switching. Plain `useTranslation` from `react-i18next` works too, but you have to load the namespace yourself.

The locale files are flat JSON, one key per phrase:

```json
{
  "welcome": "Welcome",
  "logout": "Log out"
}
```

> **Restart `pnpm dev` after adding or renaming a key.** i18next loads each
> namespace's resources once at init and does **not** hot-reload locale JSON
> into its in-memory store. A key you add while the dev server is running
> renders as the raw key (e.g. `my-plugin:welcome`) until you restart. A
> production build always bundles the current keys, so this is a dev-loop
> quirk only — not a missing-translation bug.

## Key parity

The contract test's `expectI18nKeyParity()` fails when locale files for the same namespace have mismatched key sets. So if `en.json` has `"welcome"`, `de.json` must too. This catches the common drift where someone adds an English key and forgets the others.

To opt out for a specific locale, omit it from the locales list passed to `expectI18nKeyParity(locales)` — see [`@oc-mui/plugin-testing`](../../packages/plugin-testing/README.md).

## Conventions

- **Namespace names** are kebab-case and match the plugin id, or `<plugin-id>-<surface>` if you split UIs (`my-plugin-header`, `my-plugin-sidebar`).
- **Key names** are scoped semantically (`buttons.save`, `errors.network`), not by component path. Restructuring components shouldn't break translations.
- **Don't** reference another plugin's namespace. Add the key to your own.
