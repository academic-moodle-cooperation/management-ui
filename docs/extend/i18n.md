# Translations

For plugin developers shipping more than one language. Afterwards you'll have translated strings that render in both environments and pass the contract test's key-parity check.

Each plugin owns one or more **namespaces**, declares them in `plugin.json`'s `i18nNamespaces`, and the host loads and switches locales for you. Below: the layout that makes that work — the multi-module case first (the main consumer of this mechanism), the single-bundle case after.

## The mechanism

- A **namespace** groups one UI's strings: kebab-case, `<plugin-id>` or `<plugin-id>-<module>`.
- `plugin.json` declares every namespace the plugin ships in `i18nNamespaces` (multi-module manifests can also declare them per `modules[]` entry).
- Locale files are plain JSON, one file per language, per namespace: `locales/<namespace>/<lng>.json`.
- Components resolve keys as `t("<namespace>:<key>")` via `usePluginTranslation` from `@oc-mui/i18n`.
- The host serves the files and tells i18next where they live — in dev via the `.local-plugins` manifest, in production via the JAR's `plugins.json` entry (`localesUrl` + namespace list). You never wire i18next yourself.

## Worked example: an org plugin

An org plugin (its own repo, mounted at `.local-plugins/<org>/`, shipped as a JAR) is typically multi-module, and each module carries its own namespace and locale folder:

```
.local-plugins/acme/
├── plugin.json                # "i18nNamespaces": ["acme-header", "acme-footer"]
└── modules/
    ├── header/
    │   ├── locales/
    │   │   └── acme-header/
    │   │       ├── en.json    # { "logout": "Log out" }
    │   │       └── de.json    # { "logout": "Abmelden" }
    │   └── … module code
    └── footer/
        └── locales/
            └── acme-footer/
                ├── en.json
                └── de.json
```

```tsx
import { usePluginTranslation } from "@oc-mui/i18n";

export function AcmeHeader() {
  const { t } = usePluginTranslation(["acme-header"]);
  return <button>{t("acme-header:logout")}</button>;
}
```

`usePluginTranslation` auto-loads the namespace on first render and follows the host's locale switching. (Plain `useTranslation` from `react-i18next` works too, but then loading the namespace is your problem.)

That's the whole authoring story. Serving is automatic in both environments:

- **Dev** (`pnpm dev` with the plugin under `.local-plugins/`): the dev server discovers every locale folder — root-level `locales/<ns>/` (or the directory named by `plugin.json`'s `locales` field) as well as `modules/*/locales/<ns>/` — serves the files, and announces the namespaces in `/local-plugins/manifest.json` — the shell registers them with i18next on load.
- **Production (JAR)**: the locale folders ship inside the JAR; the backend reads your `i18nNamespaces` (and `locales`, if you relocated the folder) out of `plugin.json` and lists each plugin's namespaces and locale URL in `plugins.json`, and the shell registers them the same way. A JAR *without* a `plugin.json` declares its namespaces in the `Management-Plugin-I18n` manifest header instead — the fallback path, described in [Backend bundles](./backend-bundles.md#two-discovery-strategies-and-which-wins).

## Single-bundle plugins (the scaffold layout)

A scaffolded single-bundle plugin keeps its locales at the plugin root — no `modules/`:

```
.local-plugins/hello/
├── plugin.json                # "i18nNamespaces": ["hello"]
└── locales/
    └── hello/
        ├── en.json
        └── de.json
```

This is the canonical manifest layout: the contract test's parity check reads it, and the scaffolded JAR build ships it. A different location can be declared via `plugin.json`'s `locales` field (a relative path with the same `<locales>/<namespace>/<lng>.json` structure inside).

The `.local-plugins` dev server discovers this layout too (including a relocated `locales` root), so the strings render live under `pnpm dev` just like the modules layout. When both layouts ship the same namespace, the root-level files win.

## Two rules the tooling enforces

**Key parity.** The contract test's `expectI18nKeyParity()` fails when locale files of the same namespace have mismatched key sets — if `en.json` has `"logout"`, `de.json` must too. Keys may be nested; parity compares dotted paths (`buttons.save`). To check only specific locales, pass them: `expectI18nKeyParity(["en", "de"])` — see [`@oc-mui/plugin-testing`](../../packages/plugin-testing/README.md).

**No hot reload for locale JSON.** i18next loads each namespace once at init. A key added while `pnpm dev` runs renders as the raw key until you **restart the dev server**. Production builds always bundle the current keys — this is a dev-loop quirk, not a missing-translation bug.

## Language selection and dates

Two things are host-level, not per-plugin:

- **Which language the UI starts in.** `app.locale` in `config.json` is the deployment default; a user's pick from the language switcher is remembered and wins from then on. Plugins never need to read it — `t(...)` follows whatever is active.
- **Dates.** Format them with `formatDate` from `@oc-mui/i18n`, never with a hardcoded `new Intl.DateTimeFormat("de-DE", …)`. `formatDate` takes the locale from the active language and returns `""` for unusable input instead of throwing inside a table cell.

```tsx
import { formatDate } from "@oc-mui/i18n";

<span>{formatDate(episode.startDate)}</span>                        // medium date + short time
<span>{formatDate(series.created, { dateStyle: "long" })}</span>    // any Intl option set
```

## Labels the host renders for you

Some extension points render a caption *outside* your component — a sidebar tab's reiter, for one. Your own `t(...)` never runs there, so pass the key at registration and let the host resolve it:

```ts
manager.registerComponent("table-sidebar:episodes:tabs", MyTab, {
  key: "exam-recordings",
  label: "acme:tabs.examRecordings",
});
```

Same convention as `sidebar:nav-items`, whose `title` is a translation key too. See [`plugins/core/README.md`](../../plugins/core/README.md) for the catalogue and the fallback rules.

## Conventions

- Namespace names: kebab-case, `<plugin-id>` or `<plugin-id>-<module>` (`acme-header`, `acme-footer`).
- Key names: scoped semantically (`buttons.save`, `errors.network`), not by component path — restructuring components shouldn't break translations.
- Don't reference another plugin's namespace; add the key to your own.
